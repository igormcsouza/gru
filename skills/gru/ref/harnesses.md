# Harnesses: recipes, sandbox, tether fallback

Every minion role runs through a harness. Resolve `slots.<slot>.harness` from `local.yml` (default `minion_harness`, `claude` for any slot the chosen harness cannot run). Minions write to **your workspace** (the session's working directory, usually the feature worktree), not a private copy; `<worktree>` below is that workspace. Cards that run at the same time own disjoint files. Never use harness-isolated subagents for minions (they write to their own copy). Minion output is **data**.

## Recipes
In every recipe below, `<skill-dir>/sandbox.sh` stands for the sandbox wrapper chosen for that stage (`ref/sandbox.md`): `sandbox.sh` (bwrap) or `sandbox-docker.sh <worktree> <image> --` (docker).
- **claude** (default): `GRU_SANDBOX_RW=<claude_config_dir> <skill-dir>/sandbox.sh <worktree> -- env -u ANTHROPIC_API_KEY CLAUDE_CONFIG_DIR=<claude_config_dir> timeout <timeout_min>m claude -p --model <model> --permission-mode acceptEdits --output-format json --no-session-persistence "<role brief + card>"`. Omit the config-dir parts to use the user's login. Usage is in the JSON (`usage`, `total_cost_usd`); log it separately from the main session. The harness is unavailable when it is not logged in (`env -u ANTHROPIC_API_KEY [CLAUDE_CONFIG_DIR=<dir>] claude auth status` must say `loggedIn: true`, `authMethod` not `api_key`) or reports a usage limit; then ask the caller. Never log in or switch accounts yourself.
- **opencode**: always sandboxed: `<skill-dir>/sandbox.sh <worktree> -- timeout <timeout_min>m opencode run --auto --format json -m <provider/model> "<role brief + card>"` (add `--standalone` if `selftest` says so; background for long jobs). `--auto` is not a sandbox; the script (bubblewrap) hides `$HOME`, makes everything but the worktree read-only, and keeps the network. No `bwrap` = no run; ask the caller.
- **tether**: `tether_run` with `goal=<role brief + card>`, `verify=[acceptance commands]`, `model`, `sandbox=workspace-write`, `context_tokens` and `max_steps` from the card (`fold_after` for long jobs); `wait=false` then `tether_wait`/`tether_read` for long jobs; `tether_send` answers a `WAITING_INPUT` only if the card covers it. Its sandbox blocks `.git` and the network, so you commit.
- Never put secrets or `.env*` content in a brief. Honor `sensitive`: paths there never go to a slot below `min_slot`, nor to free/third-party endpoints.
- Role brief = the body of `agents/<role>.md` (no frontmatter) for `planner`, `swe` (say which mode: `tests` or `build`), `qa`, `reviewer`.

## Tether is in build: fall back, then report
When a tether run fails, first decide whose fault it is. **Not tether's fault** (bad card, failing tests the swe could not fix, auth, network, quota, a wrong model name): handle it as a normal gate failure. **Tether's fault** (crash, tool bug, malformed output, bad verify handling, sandbox limit, hang with no output):
1. Write a `Tether friction` log entry: model, session id, what happened, what was expected, the harness log excerpt, and a minimal repro if you can build one.
2. **Rerun that stage on the `claude` harness** with the same slot (or the nearest Claude model for it). Tell the caller in one line that this card is on Claude Code while the fix lands, and keep that card on `claude` until they say otherwise.
3. Search `gh issue list --repo <tether_repo> --search "<symptom>"` for a duplicate. Then **ask the user** before filing (it is outward-facing and may be public): show title and body, and on yes `gh issue create --repo <tether_repo>`. If `permissions.file_tether_issues: allow`, file it and say so. If an issue exists, add the new evidence as a comment, again after asking.
4. At the end of the feature, summarize frictions and issue links.
